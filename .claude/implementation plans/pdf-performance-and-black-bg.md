# PDF Performance and Black Background

## 1. Goal

The PDF deck viewer currently has three problems: the initial ~15MB download feels very slow with no way to start viewing sooner, switching pages still visibly re-renders each time (even pages already viewed), and there is a brief flash of the site's default off-white background before the viewer's own black background takes over. This plan addresses all three.

## 2. Current System Behaviour

`app/(portal)/portal/[token]/pdf-file/route.js` resolves the deck's upstream Kirby PDF URL (cached in-memory for 5 minutes via `pdfUrlCache`), then performs a single unranged `fetch(pdfUrl)` against the upstream host on every request and streams the response straight through. No response bytes are cached — every browser request to this route, including a second view of the same deck in the same session, re-downloads the full file from Kirby.

`components/DeckPdfViewer.js` sets `DOCUMENT_OPTIONS` with `disableStream: true` and `disableRange: true`, meaning `react-pdf`/pdf.js waits for the entire response body to arrive before parsing anything or rendering the first page — there is no way to begin viewing until the full ~15MB has downloaded. Once loaded, `<Page pageNumber={currentPage} .../>` is the only `Page` element rendered at a time; navigating to a different page unmounts the current `Page` and mounts a new one for the new `pageNumber`, causing pdf.js to re-render that page's canvas from scratch — this happens even when returning to a page that was already viewed earlier in the session, since nothing is retained.

`app/(portal)/layout.js` renders `<div className="portal-shell min-h-screen"><div className="portal-content">{children}</div></div>` with no background styling of its own. The site's global `html`/`body` background comes from `style-guide.css`'s `--color-bg` custom property, which defaults to `#F0EFEB` (off-white) at `:root`, only switching to black via `--color-text`/`--color-bg` swap when an `html.dark` class is present — which nothing in the portal route currently applies. `.deck-pdf-viewer`'s own `background-color: #000000` (in `deck.css`) only exists on a `div` rendered by the client component `DeckPdfViewer`, which only appears in the DOM after client-side JS mounts — so on first paint (server-rendered HTML, before hydration/mount), the page shows the default off-white background, followed by a flash to black once `DeckPdfViewer` mounts.

## 3. Desired Behaviour

**Download speed:** The first time any given deck's PDF is requested, the proxy fetches and caches the full byte payload in memory. Any subsequent request for the same deck (same client re-opening it, a page reload, or a second client viewing the same deck within the cache window) is served instantly from memory without re-contacting the upstream Kirby host. Additionally, pdf.js begins parsing/rendering the first page as bytes stream in over the single connection, rather than waiting for the complete file — so the perceived wait before the first page appears is shorter even on a cold (uncached) load, without reintroducing the multiple small range requests that were previously found unreliable.

**Per-page delay:** The first time a given page is visited, it renders as it does today. Every subsequent visit to that same page within the same viewing session is instant, because its already-rendered canvas is kept in the DOM (hidden, not unmounted) rather than being torn down and rebuilt.

**Background:** The portal route (all states — locked, expired, not-ready, Figma embed, and the PDF viewer) renders black from the very first server-rendered HTML, so there is no flash of the off-white site background at any point before or during client-side hydration. This is scoped to the portal route only; the rest of the site keeps its existing off-white default.

## 4. Architecture Considerations

**Byte caching** replaces the existing `pdfUrlCache` pattern's "cache the resolved URL, refetch bytes every time" behavior with also caching the bytes themselves, keyed by token. Given the confirmed usage pattern (roughly two decks per client, low concurrent volume), an in-memory `Map` with a modest cap (e.g. 10 entries) and a longer TTL than the URL cache (30 minutes, versus the existing 5-minute URL TTL) is appropriate — the bytes themselves don't need to be re-validated as often as the resolved URL does, and the low volume means memory pressure from a handful of ~15MB buffers is not a practical concern. This is a plain in-memory cache (no Redis/external store) consistent with the existing `pdfUrlCache` approach in the same file, so no new infrastructure or dependency is introduced. As with the existing URL cache, this cache is per-server-instance and does not persist across deployments/restarts or apply across multiple server instances if the app is horizontally scaled — this is an accepted limitation matching the existing pattern's own limitation.

**Streamed (not ranged) loading**: `disableStream` is set back to `false` while `disableRange` remains `true`. This is a deliberate middle ground versus the two prior approaches: full ranged loading (many small requests, previously found unreliable) versus fully blocking full-download (previous plan, correct but slow to first paint). With `disableStream: false` and `disableRange: true`, pdf.js still issues exactly one HTTP request for the whole file (no additional request volume, no reintroduction of the range-request reliability problem), but reads and processes the response incrementally as bytes arrive, allowing document structure parsing and first-page rendering to begin before the full body has finished downloading. This trades a small amount of the "always a clean single complete fetch" simplicity from the prior plan for meaningfully faster time-to-first-page, which is judged worth it given the explicit complaint about wait time.

**Per-page render caching** is done by changing `DeckPdfViewer` to track the set of page numbers that have ever been the `currentPage`, and rendering a `Page` element for every page in that set simultaneously (not just the current one), toggling each one's visibility via CSS rather than mounting/unmounting. This keeps react-pdf's internal render state and painted canvas alive for every visited page. The lazy approach (render-on-first-visit, keep after) is chosen over eager (render-all-upfront) specifically to avoid a large deck causing a long freeze immediately after document load, per the user's decision — the tradeoff is that the very first visit to each page still pays a render cost, only repeat visits are instant.

Toggling visibility (rather than e.g. `display: none` unmounting via conditional rendering) must be done in a way that doesn't cause react-pdf to re-run its render pipeline — using a wrapping element per page whose CSS `display` is toggled between `block`/`none` based on whether it's the active page keeps the `Page` component itself mounted throughout, which is what preserves its rendered canvas. Layout/sizing (`fitWidth`) must still apply correctly to whichever page is currently visible; since only one page is ever visible at a time (others are `display: none` and take no layout space), stacking them is safe using absolute or standard block layout without needing extra positioning logic beyond what already centers the single visible page today.

**Background fix**: rather than touching the shared `--color-bg` custom property (which would affect the token's meaning sitewide) or waiting for client-side JS to paint over a flash, a server-rendered class is added directly in `app/(portal)/layout.js` — since this is a server component, whatever class/style it outputs is present in the very first HTML response, eliminating the flash entirely rather than racing it. This keeps the change scoped precisely to the portal route tree without altering global theme variables used elsewhere on the site.

No new dependencies are introduced by any part of this plan.

## 5. Data Flow

**Proxy byte caching**: `GET` request arrives at `pdf-file/route.js`. Access is gated via the existing session-cookie check (unchanged). The route now checks a new `pdfBytesCache` Map keyed by token before doing any upstream fetch; on a hit within the TTL, it responds directly from the cached buffer with the same headers as today, with no upstream request made at all. On a miss (or expired entry), it performs the upstream fetch as today, but additionally buffers the full response body (via `upstream.arrayBuffer()` or by teeing the stream) and stores it in `pdfBytesCache` before/while streaming it to the client, so the next request can be served from cache.

**Streamed loading**: unchanged network path otherwise — `DeckPdfViewer`'s `<Document file={pdfUrl}>` still requests the same proxy URL exactly as before; only the client-side pdf.js processing behavior changes (incremental parsing of the single response instead of waiting for it to fully complete), which is purely a `DOCUMENT_OPTIONS` change with no proxy-side implication.

**Per-page render caching**: `DeckPdfViewer` already owns `currentPage` state. A new derived/tracked set of "ever-visited" page numbers is updated whenever `currentPage` changes (adding the new value if not already present). Rendering maps over this visited-pages set (not just `[currentPage]`) to produce one `Page` element per visited page, each wrapped in a container whose visibility is toggled based on equality with `currentPage`. No new data enters from outside the component; this is purely a change to what `DeckPdfViewer` renders based on state it already tracks.

**Background**: no data flow change — this is a pure rendering/styling change in a server component that requires no client state or props.

## 6. Component Responsibilities

### `app/(portal)/portal/[token]/pdf-file/route.js` (modified)
**Responsible for:** access gating (unchanged), resolving the upstream PDF URL (unchanged, via existing `pdfUrlCache`), now also caching and serving the actual PDF byte payload keyed by token with its own TTL and entry cap, falling back to a fresh upstream fetch on a cache miss/expiry/eviction.
**Not responsible for:** cache invalidation triggered by the underlying PDF changing in Kirby — if a deck's file is replaced upstream within the TTL window, the cached bytes will still be served until expiry, matching the existing tradeoff already accepted for the URL cache's own TTL.
No props/state (route handler); the new cache is module-level, matching the existing `pdfUrlCache` pattern.

### `DeckPdfViewer` (modified)
**Responsible for:** as before, plus: tracking which page numbers have been visited, rendering a `Page` for each visited page (not just the current one), toggling their visibility via CSS rather than mount/unmount, and enabling streamed (non-ranged) document loading via `DOCUMENT_OPTIONS`.
**Not responsible for:** any cap on how many rendered pages are retained — per the lazy/keep-after-visit decision, all visited pages accumulate for the duration of the viewing session with no eviction, since a full deck being visited page-by-page is bounded by `numPages` itself and the earlier decision was explicitly to avoid the eager all-at-once cost, not to add a new eviction mechanism.
No prop shape changes. New internal state: a set (or equivalent) of visited page numbers, in addition to existing `currentPage`/`numPages`/etc.

### `app/(portal)/layout.js` (modified)
**Responsible for:** applying a black background to the portal route tree from the first server-rendered HTML.
**Not responsible for:** per-state styling differences (PasswordGate, expired/not-ready text, Figma embed, and the PDF viewer all sit on top of this same black background — none of them need their own background override as a result of this change, though their foreground text/content must remain legible against black, see Edge Cases).
No prop/state changes — this is a static class addition to existing server-rendered markup.

## 7. Files Affected

- `next/app/(portal)/portal/[token]/pdf-file/route.js` — add byte-level caching alongside the existing URL cache.
- `next/components/DeckPdfViewer.js` — set `disableStream: false`, add visited-page tracking and render-all-visited/toggle-visibility rendering.
- `next/styles/deck.css` — add a CSS rule for toggling per-page visibility (the wrapper class used to show/hide each rendered page).
- `next/app/(portal)/layout.js` — add a black-background class to the portal shell.
- `next/styles/style-guide.css` or a portal-scoped stylesheet — define the actual black-background class/rule referenced by `layout.js` (exact file to hold the new rule depends on whether a portal-specific stylesheet already exists — see Step-by-Step for the concrete decision).

## 8. Step-by-Step Implementation

**Step 1 — `pdf-file/route.js`: add byte-level caching**
Add a new module-level cache alongside `pdfUrlCache`, e.g. `pdfBytesCache = new Map()`, storing entries as `{ body: ArrayBuffer, contentType, contentLength, cachedAt }`. Define constants for the new TTL (30 minutes) and a max entry count (10) near the existing `CACHE_TTL_MS`. In the `GET` handler, after resolving `pdfUrl` and before the upstream `fetch`, check `pdfBytesCache` for a non-expired entry keyed by `params.token`; if found, respond immediately with a `NextResponse` built from the cached buffer and stored headers, skipping the upstream fetch entirely. On a miss, perform the upstream fetch as today, but read the full body into memory (e.g. `await upstream.arrayBuffer()`) rather than streaming `upstream.body` directly through — this is a necessary behavior change from today's pure passthrough, since the bytes must be fully collected once in order to be both cached and returned; store the resulting buffer (plus the resolved headers) in `pdfBytesCache`, evicting the oldest entry first if the cache is at its cap, then return a `NextResponse` built from that buffer. Gotcha: switching from streaming `upstream.body` to buffering via `arrayBuffer()` means the response to the client is no longer sent progressively as it arrives from upstream — it is now held until the full upstream download completes, then sent to the client in one piece. This is an acceptable tradeoff given the cache's purpose (this only affects requests during the *first, uncached* fetch of a given deck — cached hits are unaffected and are actually faster than before), and does not defeat the separate streamed-loading improvement in Step 2, since Step 2's improvement is about the *browser's* fetch of the proxy response being processed incrementally by pdf.js, which still applies to the bytes as NextResponse streams them to the browser even though the proxy itself now waits for the full upstream body first on a cache miss.

**Step 2 — `DeckPdfViewer.js`: re-enable streamed loading**
In `DOCUMENT_OPTIONS`, change `disableStream: true` to `disableStream: false`. Leave `disableRange: true` and `disableAutoFetch: true` unchanged. Gotcha: confirm this does not reintroduce range requests — `disableRange` independently controls that, and remains `true`, so only one HTTP request is still made per document load; `disableStream` only controls whether that single response is consumed incrementally or awaited in full.

**Step 3 — `DeckPdfViewer.js`: track visited pages**
Add `const [visitedPages, setVisitedPages] = useState(() => new Set([1]));` (page 1 is always the initial page, so it starts pre-visited). Add a `useEffect` keyed on `[currentPage]` that adds `currentPage` to `visitedPages` if not already present (using the functional `setVisitedPages` form to add to the existing set immutably, e.g. by constructing a new `Set` from the previous one plus `currentPage`). Gotcha: `Set` objects must be replaced (not mutated in place) for React to detect the state change and re-render — always create a new `Set` instance when adding a page.

**Step 4 — `DeckPdfViewer.js`: render all visited pages, toggle visibility**
Replace the single conditional `{numPages && <Page pageNumber={currentPage} ... />}` block with a loop over `Array.from(visitedPages)`, rendering one wrapping element per visited page number (e.g. a `div` with `className="deck-pdf-viewer__page"` plus a modifier class such as `deck-pdf-viewer__page--active` applied only when that page number equals `currentPage`), each containing a `Page` element identical to today's (`pageNumber={pageNumber}`, `width={fitWidth}`, same `onLoadSuccess`/`loading` props) but keyed by `pageNumber` so React preserves each one across re-renders rather than remounting. The `onLoadSuccess` callback that sets `pageAspectRatio` should only act the first time it fires overall (it already guards with `if (pageAspectRatio === null)`, which continues to work correctly since it will simply be a no-op for every page after the first one that loads). Gotcha: `Page` elements are currently direct children of `Document`; confirm `react-pdf`'s `Document` component tolerates multiple simultaneous `Page` children (it does — this is a standard supported usage pattern for rendering multiple pages of the same document) rather than assuming only one `Page` may be mounted at a time.

**Step 5 — `deck.css`: add page visibility toggle styling**
Add a `.deck-pdf-viewer__page` rule that positions each page wrapper absolutely within `.deck-pdf-viewer` (matching how the current single `Page` is centered by its parent's flex `align-items`/`justify-content`) and sets `display: none` by default, with a `.deck-pdf-viewer__page--active` modifier setting `display: block` (or `flex`, matching whatever layout is needed to preserve the existing centering behavior). Gotcha: `.deck-pdf-viewer` is currently a flex container centering its single child; with multiple stacked children now present (only one visible at a time), confirm the active page still centers correctly — since inactive pages are `display: none` and contribute no layout box, the flex centering of the one remaining visible child should behave identically to today, but this should be visually verified (see Test Considerations) since absolute-positioning the wrappers may be needed instead if flex-with-hidden-siblings doesn't center as expected in practice.

**Step 6 — `layout.js`: apply portal-scoped black background**
Add a new class to the outer `portal-shell` div, e.g. `portal-shell--dark` (or fold the styling into `portal-shell` itself if `portal-shell` is not used/styled anywhere outside the portal route — confirm this before deciding, since `portal-shell` as a class name may already carry meaning elsewhere in `nav.css`/`style-guide.css` that must not be disturbed). This class must be applied unconditionally in the server component's JSX (not conditionally by content type), so it is present in the initial HTML for every portal state per the confirmed decision to cover the whole route. Gotcha: verify no existing selector already targets `.portal-shell` with background rules that would conflict — search `nav.css` and `style-guide.css` for `portal-shell` before adding the new class, to avoid an unintended cascade conflict.

**Step 7 — new/existing stylesheet: define the black background rule**
Add the actual CSS rule for the class introduced in Step 6, setting `background-color: #000000` (and, if needed for legibility, a default `color: #ffffff` at this scope so PasswordGate/expired/not-ready text — which currently rely on the site's default dark-on-light text color — remains readable against black; see Edge Cases). Place this rule in whichever stylesheet already owns portal-shell-level styling (`style-guide.css` if `.portal-shell` is defined there, otherwise the most relevant existing portal-related stylesheet) rather than introducing a new CSS file, to match the existing convention of colocating related rules by section comment blocks (as seen in `deck.css`).

## 9. Edge Cases

- **Deck replaced/updated in Kirby while bytes are still cached (up to 30 minutes):** viewers will see the stale cached version until the TTL expires — an accepted tradeoff matching the existing URL cache's own staleness window, and low-risk given decks are described as static per-client assets, not frequently updated.
- **Two different clients' decks both cached simultaneously:** bounded by the 10-entry cap; given the confirmed ~2 decks per client and generally low concurrent traffic, this cap is expected to comfortably cover realistic concurrent usage without thrashing (oldest-entry eviction only kicks in beyond that).
- **A cache miss occurs while another request for the same token is already in flight (two tabs opening the same deck simultaneously before it's cached):** each request independently fetches and writes to the cache; the second write simply overwrites the first with equivalent bytes — no corruption, just briefly duplicated upstream work, matching how the existing URL cache already tolerates the same race.
- **Streamed loading (Step 2) on a very slow/unstable connection:** if the connection drops mid-stream, pdf.js's existing `onLoadError` handling (already wired to `console.error`) covers this exactly as it would for the previous full-download approach — no new failure mode is introduced, only a difference in when partial data has already been used for rendering versus discarded entirely on error.
- **A visited page's underlying content depends on something that could change during the session (not applicable here — decks are static PDFs, pages don't change while being viewed):** no invalidation logic is needed for the visited-pages cache; it is safe to assume a page, once rendered, remains valid to keep for the rest of the session.
- **Very large deck where a viewer pages through most/all of it:** worst case converges toward the eager-render cost the lazy approach was chosen specifically to avoid paying immediately — but spread out over the course of normal navigation rather than all at once up front, which was the explicit reason lazy was preferred.
- **Text/content legibility on PasswordGate, expired, and not-ready screens once the background is black:** these currently render plain text with the site's default (dark-on-light) text color; switching the shared portal background to black without also addressing text color would make these screens unreadable. This must be handled in Step 7 by also setting an appropriate light text color at the same scope, or those specific components will need their own explicit color overrides — flagged here as a required follow-up check during implementation, not deferred silently.

## 10. Test Considerations

No automated test suite exists for this app; none introduced by this plan. Manual checks:
- Open a deck for the first time (cold cache) and confirm, via the Network tab, the proxy still returns the full file, and observe whether the first page appears noticeably sooner than before (streamed parsing) even though total download time is unchanged.
- Reload or reopen the same deck within 30 minutes and confirm (via Network tab and/or server logs, if added temporarily during testing) that the proxy responds without making an upstream request to Kirby.
- Page forward through a deck, then page back to earlier pages, and confirm later visits to already-seen pages show no visible re-render delay.
- Confirm memory/behavior remains reasonable when paging through an entire large deck once (visited-pages set grows to `numPages`).
- Load the portal route in each state — locked (PasswordGate), expired, not-ready, Figma embed, and PDF viewer — and confirm the background is black immediately on first paint in every case, with no flash of off-white, and that all text remains legible.
- Specifically check PasswordGate's input field and any button styling against the new black background for contrast/legibility.
- Confirm the previously-completed PDF-full-preload plan's behavior (single request per fresh load, progress bar, disableRange) still functions correctly alongside these changes — this plan builds on top of that one rather than reverting it.

## 11. Implementation Order

1. `next/app/(portal)/portal/[token]/pdf-file/route.js` — modified first: byte caching is independent of the other changes and establishes the faster-repeat-load foundation before touching client rendering behavior.
2. `next/components/DeckPdfViewer.js` — modified second: streamed loading (Step 2) and visited-page rendering (Steps 3-4) are grouped together since they're both in this file and both affect the same rendering logic; streamed loading is applied first within this file since it's the simpler, more contained change.
3. `next/styles/deck.css` — modified third: the page-visibility CSS depends on the wrapper class names introduced in `DeckPdfViewer.js`, so it follows that file.
4. `next/app/(portal)/layout.js` — modified fourth: independent of the PDF-specific changes above; ordered after them simply to keep the performance-related file group together before the background fix.
5. Whichever stylesheet is chosen in Step 7 (`style-guide.css` or existing portal stylesheet) — modified last: depends on the class name introduced in `layout.js`, so it must follow that file.
